# AgentDesk 项目全景

> 一页纸看清：**做了什么、现在怎么用、要不要上公网、下一步是什么**。
>
> 最后更新：2026-09-27

---

## 0. 一句话说清它是什么

> **一个 HTTP 服务：门口 24 个路由，里面靠「模型调用 + 私有知识检索 + 工具执行」
> 三条腿走路；写操作停下来等人批准，每一步都留痕、可查成本。**

它不是一个聊天框。区别在于：**聊天框是你去用它；它是一个地址，别的系统可以来调它。**
所以它可以被告警系统触发 —— 凌晨三点你在睡觉，它自己起来诊断。

## 1. 现在能用吗

**能用。现在就能。** 三条命令：

```bash
cd "E:/Workbuddy/ai agent/agentdesk"
.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
# 然后浏览器打开 http://127.0.0.1:8000
```

打开根路径就是一张导航页：这是什么、有哪些能力、从哪开始试。

**实测结果**（真实本机运行，不是设计说明）：

| 检查项 | 结果 |
|---|---|
| 服务版本 | `0.9.0`，24 个路由，实测全部 200 |
| 沙箱 | 后端 `docker`（**真隔离=True**，十项限制逐条实测）· **fail-closed=True** |
| 白名单 | 13 条（直通 10 / 需审批 3）· 高危拦截 **42 个二进制** |
| Agent 工具 | 7 个（6 只读 + 1 高危 `run_command`） |
| 真实诊断 | `intent → knowledge → diagnose → verify → finalize`，5 次工具调用、9.7s、校验通过 |
| 库外问题 | 明确说明「kafka 不在监控范围内」并给出工具返回作为证据 |
| 成本看板 | P95 **11167ms**（单次请求口径）· 缓存命中率 54% |

> **两种"不知道"**：问它知识库里没有的运维问题 → 它说「**知识库中没有相关内容**」；
> 问它监控范围外的主机 → 它逐台查完工具，说「**目标主机 kafka 不存在，已知主机只有
> web-01/db-01/cache-01**」。**都是刻意设计的，不是能力不足。**

## 2. 五种用法（按上手难度排）

### ① 打开线上地址点着用 —— 最省事

```
https://agent.simosheng.fun/try
```

填令牌 → 填问题 → 点「开始」。返回里带完整执行轨迹（它自己决定了查什么、跑几轮）。

访问令牌在服务器 `/opt/agentdesk/.env` 的 `AGENT_TOKEN` 那一行。
这个实例开了鉴权：除 `/`、`/try`、`/health`、`/docs` 之外都要令牌。

### ② `/docs` 交互式文档 —— 开发者的调法

```
http://127.0.0.1:8000/docs         # 本地（未开鉴权，直接可用）
https://agent.simosheng.fun/docs   # 线上（先点右上角 Authorize 填令牌）
```

找到 `POST /agent/ask` → "Try it out" → 填：

```json
{"question": "web-01 上的网站访问很慢，有时报 502，帮我看下原因",
 "engine": "supervisor"}
```

`engine` 有三档：`handwritten`（手写 ReAct 循环）／`langgraph`（状态图）／`supervisor`（多 Agent 编排）。

> 线上实例**必须先点 Authorize 填令牌**，否则每个请求都是 401。
> 鉴权是在中间件里做的，对框架是黑盒，所以这个声明是单独写进
> OpenAPI schema 的 —— 目的就是让 Swagger UI 把那个按钮渲染出来。

### ③ 命令行（不起服务也能用一部分）

```bash
# RAG 检索与问答
.venv\Scripts\python.exe -m app.rag.pipeline ask "nginx 报 502 怎么排查"
.venv\Scripts\python.exe -m app.rag.pipeline build      # 重建索引
.venv\Scripts\python.exe -m app.rag.pipeline eval       # 召回率评测

# Agent 诊断（带完整轨迹）
.venv\Scripts\python.exe -m app.agents.graph "cache-01 上的 Redis 容器一直重启"
.venv\Scripts\python.exe -m app.agents.supervisor --graph   # 看编排图

# MCP Server（给 Cursor 之类客户端用）
.venv\Scripts\python.exe -m app.mcp_server.server
.venv\Scripts\python.exe -m app.mcp_server.server --check   # 工具清单 + schema 校验
```

### ④ 一条命令自检 —— 改完代码先跑这个

```bash
.venv\Scripts\python.exe scripts\smoke_test.py            # 九层快速自检（不花钱）
.venv\Scripts\python.exe scripts\smoke_test.py --full     # 含真实 Agent 调用
.venv\Scripts\python.exe scripts\security_check.py        # 公网安全层 23 项
```

**九层**：环境 → 模型 → 检索 → Agent → 沙箱 → 观测 → 评测 → MCP → HTTP 接口。
退出码 0 = 全通，可以接进自动化。

### ⑤ 现场演示

```bash
.venv\Scripts\python.exe scripts\demo.py    # 走完上面那张表的全部检查
```

## 3. 架构全景

```
调用方：值班工程师（人）  /  告警系统（Alertmanager webhook）  /  Cursor 等 MCP 客户端
                              │
        ┌─────────────────────┴─────────────────────┐
        │              app/main.py                  │  ← 大门（24 个路由）
        │      接请求 → 校验 → 调能力 → 返回 → 留痕   │
        └──┬──────────┬───────────┬─────────────────┘
           │          │           │
   ┌───────▼──────┐   │   ┌───────▼──────────┐
   │ app/agents/  │   │   │ app/mcp_server/  │  ← 第二个出口（给外部客户端）
   │  编排层      │   │   │ 7 tools + 2 res  │
   │  Supervisor  │   │   └───────┬──────────┘
   │  + 5 专业    │   │           │
   │    Agent     │   │           │
   └───┬──────┬───┘   │           │
       │      │       │           │
       │  ┌───▼───────▼───────────▼───┐
       │  │      app/tools/           │  ← 唯一的工具实现（7 个）
       │  │  6 只读 + run_command     │
       │  └───┬───────────────────┬───┘
       │      │                   │
       │  ┌───▼────────┐   ┌──────▼──────────────────┐
       │  │ app/rag/   │   │ app/sandbox/            │  ← 写操作专用通道
       │  │ 私有知识    │   │ policy → approvals →    │
       │  │ 6 篇 / 50块 │   │ executor（一次性容器）   │
       │  └────────────┘   └─────────────────────────┘
       │
   ┌───▼────────────────────────────┐
   │ app/llm.py                     │  ← 模型调用唯一入口
   └───┬────────────────────────────┘
       │
   ┌───▼──────────┐
   │ DeepSeek API │
   └──────────────┘

横切两层（所有请求都经过）：
  app/observability/   每次运行一条 trace：token / 成本 / 耗时 / 每个 Agent 花了多少
  app/evaluation/      判定层：4 项规则 + 模型判分 + 判定器自证
```

**一条设计主线**：每一层只依赖它下面那层，不反向依赖。
所以「换模型」只动 `llm.py`，「换工具实现」只动 `tools/`，
「换编排引擎」只动 `agents/` —— **上层不用改**。

**安全的边界是结构，不是提示词**：

| 约束 | 怎么实现的 |
|---|---|
| 诊断 Agent 不能改系统 | 它的工具清单里**根本没有** `run_command`（schema 级隔离） |
| 写操作必须人批准 | 白名单策略 → 审批单 → 一次性容器，三档决策 allow/needs_approval/deny |
| 沙箱不可用不降级 | **fail-closed**：宁可拒绝执行，也不回退成直接跑 |
| 结论没过校验不许动手 | Supervisor 只在 `verdict.pass` 为真时才派处置 Agent |

## 6. 本地 vs 公网 —— 你真正该想清楚的事

### 先回答：**不部署公网，现在就能用吗？**

**能，而且完全够你自己用。** 本地跑起来之后：

- 你自己天天用（查日志、看磁盘、问知识库）
- 需要展示时**截图**（轨迹、成本看板、评测报告都能截）
- 需要讲细节时**共享屏幕**演示（比给链接更能讲清细节）

**如果只是"我自己要用"，到此为止就够了，不需要公网。**

### 那公网部署是为什么？

**不是为了你用，是为了让别人能验证。** 三条实际的理由：

**一、访客不会为了看你的项目去装环境。**

在文档里写"本地可运行"和给一个能点开的链接，**可信度差一个量级**。
访客不会 `git clone` + 建虚拟环境 + 配 API Key —— 这一步会筛掉 95% 的人。
**一个能点开的链接，是让你的项目从"声称"变成"事实"的唯一手段。**

**二、它本身就是这个项目的核心能力之一。**

这个项目的定位是 **「运维底子 + Agent 工程」**，主打 部署 / 沙箱隔离 / 可观测 / 评测。
而**部署这件事恰好是运维底子的主场** —— Nginx、HTTPS、容器、监控，本来就是这个领域的日常。
**不把它做出来，等于放着最擅长的那块能力不用。**

**三、上线会暴露本地永远遇不到的真问题。**

早先就记过一个坑：**Nginx 默认缓冲会把 SSE 流式攒够一批才转发**，
快解决方案是响应头加 `X-Accel-Buffering: no`。这类问题**只有真上线才会踩到**。
能指出"遇到过 Nginx 缓冲导致流式失效"，比空说"我了解 SSE"有说服力。

### 代价（这几条必须知道，不然会出事）

| 风险 | 具体 | 该怎么防 |
|---|---|---|
| **`/approvals` 能批准写操作** | 无鉴权公开 = 别人能批准你服务器上的命令执行 | **这个接口绝不能裸奔**，必须加 token 鉴权 |
| **`/agent/ask` 会花你的钱** | 谁都能刷，你的 API 余额会被刷光 | 加限流 + 每日额度上限 |
| 密钥泄露 | `.env` 里有 DeepSeek Key | 已经 gitignore；服务器上权限设 600 |
| 端口暴露 | 裸 uvicorn 直接对外 | 只开 443，Nginx 反代，服务只监听 127.0.0.1 |
| 证书过期 / 容器挂了 | 没人运维就是几天后打不开 | systemd 或 Docker restart policy |

### 建议：分两步，别一步到位

**第一步（现在就能做，成本几乎为零）**：本机 + 截图 + 录一段 2 分钟演示视频。
**这套演示资产完全够用了**，别为了域名和证书卡住节奏。

**第二步（上了云主机之后）**：
```
Docker Compose（应用 + Nginx + 未来接 Langfuse）
  → Nginx 反代 + HTTPS（Let's Encrypt）
  → 加两件安全措施：接口 token 鉴权 + 限流
  → 手机能打开 = 演示资产成型
```

**如果只想先拿个链接试试水**：可以用临时隧道（`cloudflared` / `ngrok`）
拿一个临时公网地址，演示完就关。
**优点是快，缺点有两个**：地址不固定（不适合长期对外公开）、
**而且它绕过了应当掌握的部署能力** —— 有点得不偿失。

> **一条硬性建议**：公网部署时，`/agent/ask`、`/approvals/*`、`/traces`
> **必须有鉴权**（可以默认关闭，公开时打开）。否则你的服务器和 API 余额都是敞开的。
> 这条在公网部署阶段一起做掉。

## 9. 一句话总结

> 一个能跑的 HTTP 服务，24 个路由，靠「模型 + 私有知识 + 工具」三条腿走路；
> **写操作卡在三道门上（白名单 → 人工审批 → 一次性容器），
> 而且知道自己不知道什么（库外拒答 100% vs 裸模型 0%）**；
> 每一步都留痕、每次运行都能算清花了多少钱。

**现在就能用。要不要上公网，取决于想"自己用"还是"让别人能验证" ——
作为对外展示的作品，后者更重要。**
