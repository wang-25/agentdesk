# 事件与出站通知

> 这份文档回答两件事：**告警进来之后去哪了**，以及**怎么让它把结论送到人手上**。
>
> 设计取舍与验收标准见 [`redev/04-design-m2.md`](redev/04-design-m2.md)。

---

## 1. 为什么要有"事件"这一层

告警是**现象**，事件是**一次故障**。

凌晨 3 点一次磁盘写满，可能同时打出 50 条告警：`DiskSpaceLow`、`NginxHighErrorRate`、
`NginxUpstreamTimeout`……它们是同一个故障在不同角度上的投影。如果每条单独处理：

| 问题 | 具体表现 |
|---|---|
| **告警疲劳** | 值班的人收到 50 条通知，然后开始无视通知 |
| **白花钱** | 模型被调用 50 次、花 50 份钱，得出 50 个互相矛盾的结论 |
| **无法复盘** | 没有任何一个地方能回答"这次故障是谁处理的" |

所以告警入口做的第一件事不是"调模型"，而是**收敛**：
按「主机 + 服务」聚合成一个事件，只诊断一次，其余告警作为成员并入。

```
告警 ──► 抑制（维护窗口）──► 聚合（主机+服务）──► 频控 ──► 建事件 ──► 推送 ──► 诊断（可选）
                                                              │
                                        GET /incidents/{id} ◄──┴──► 人：ack / resolve
```

## 2. 事件的生命周期

```
open ──ack──► ack ──resolve──► resolved ──同源新告警──► reopened ──ack──► ack ──► resolved
```

| 状态 | 含义 | 谁能改 |
|---|---|---|
| `open` | 刚建立，还没人认领 | 告警链路（自动建立）、人（ack） |
| `ack` | 有人在处理，`owner` 已记名 | 人（resolve） |
| `resolved` | 已结单，`resolution_note` 就是复盘第一手材料 | **同源新告警**（→ `reopened`） |
| `reopened` | 同一个故障又犯了 | 人（ack → resolve） |

**两条与审批单故意不同的规则**（别拿审批单的直觉套过来）：

- 审批单的 `consumed` 是**绝对终态**——重放一次就是一次未授权变更，那是漏洞。
- 事件的 `resolved` **可以被同源新告警推翻**——故障会复发，这是现实。
  "同一个故障反复发生"恰恰是最该被看见的信号，不能记成十次互不相干的故障。

`ack` / `resolve` **必须填 `by`**。与"批准必须填审批人"同一条原则：
事故复盘时，"系统自己结的"不是一个能交差的回答。

## 3. 聚合与抑制

### 3.1 聚合（`ALERT_AGGREGATE`，默认 1）

| 值 | 聚合键 | 行为 |
|---|---|---|
| `1`（默认） | `主机 + 服务` | 同机同服务的 50 条不同告警 → **1 个事件、1 次诊断** |
| `0` | `告警名 + 主机` | 完全退回改动前的精确去重语义（`decision` 与文案都一致），用于对比与回退 |

**被抑制 ≠ 被丢弃。** 窗口内重复的告警不会消失，它会：

1. 作为成员并入同一个事件（`linked_alerts`，同一指纹只算一条并计数）；
2. 在 `/webhook/alert` 的响应里带上 `incident_id` 与 `members`（"这是窗口内第几条"）。

去重表是**有界**的（`ALERT_AGG_MAX_ENTRIES`，默认 5000）：带 TTL，超限先清过期、再淘汰最旧的。
这一条是对一处真实缺陷的修复 —— 原先的 `_ALERT_LAST_SEEN` 只增不减，
不报错、不告警，只是一天天变大（那种"谁也不会注意到"的泄漏）。

### 3.2 维护窗口（抑制）

计划内变更（磁盘扩容、发版、主从切换）本来就会触发一堆告警。
不抑制的话，Agent 会认真地为你自己的维护动作做诊断并推通知 ——
**几次之后值班的人就开始无视通知了，那才是真正的事故。**

规则文件默认 `data/alert_silences.json`：

```json
[
  {"alertname_prefix": "DiskSpace", "host_prefix": "db-01",
   "until": "2026-10-03T02:00:00", "note": "磁盘扩容中（变更单 CHG-2026-101）"}
]
```

| 语义 | 说明 |
|---|---|
| 字段缺失 | 该维度**不限制** |
| 显式空串 `""` | 匹配一切（与"缺失"是两种语义，别混） |
| 忘了写 `until` / 解析不出来 | **不抑制**（fail-open） |
| 改了文件 | 不必重启（按 `mtime_ns + size` 懒加载） |

**为什么 fail-open**：抑制是"少做一件事"，这条路出错时更吵一点没关系；
反过来（解析不出来就一律静默）会把真告警藏起来，而"被藏起来的告警"是最难查的一类事故。

## 4. 出站通知怎么配

**默认完全不出站。** `NOTIFY_CHANNELS` 留空时 `build_dispatcher()` 返回 `None`，
一行网络代码都不会执行 —— 行为与加这一层之前**逐字段一致**。

```env
# 渠道多选，逗号分隔
NOTIFY_CHANNELS=dingtalk

# 钉钉自定义机器人（群设置 → 智能群助手 → 添加机器人 → 自定义）
NOTIFY_DINGTALK_URL=https://oapi.dingtalk.com/robot/send?access_token=xxx
NOTIFY_DINGTALK_SECRET=SECxxxx          # 加签密钥；不用加签可留空（公网机器人建议加签）

# 飞书 / Lark 自定义机器人
#NOTIFY_FEISHU_URL=
#NOTIFY_FEISHU_SECRET=

# 任何能收 HTTP 的系统都能接（自建告警中心、n8n、工单系统……）
#NOTIFY_WEBHOOK_URL=

NOTIFY_TIMEOUT=8          # 单渠道超时（秒）
NOTIFY_MAX_ATTEMPTS=3     # 总次数（3 = 首次 + 2 次重试）；退避 0.5s → 1s
NOTIFY_MIN_INTERVAL=60    # 同一事件 60s 内不重复推（防通知轰炸）
NOTIFY_MASK=1             # 出站脱敏（默认开，见下）
```

### 会推哪些事

| 事件 | 内容 | key（用于去重） |
|---|---|---|
| 告警处理结果 | 判定 + 主机/级别 + 事件 id + **诊断结论**（跑了的话）/ 处置预案 | `incident:{id}` |
| 待审批 | 审批单 id、命令、风险、理由、过期时间、批准入口 | `approval:{id}` |
| 执行完成 | 成功/失败 + 退出码 + 后端 + 隔离状态 + 错误 | `approval-exec:{id}` |
| 事件结单 | 处理人 + 结单说明 | `incident-resolved:{id}` |

### 三条纪律（写在代码里，也写在这里）

1. **通知是旁路。** 推不出去只留一条失败记录，绝不影响诊断结果本身。
   渠道抛异常也只是变成 `ok=False` 的结果，另一个渠道照发。
2. **200 不等于成功。** 钉钉看 `errcode`、飞书看 `code`：HTTP 200 但对端拒收
   （如关键词不匹配、签名错误）也算失败，且审计里能看出"HTTP 通了但对端拒收"。
3. **默认脱敏。** 通知是**出站**的，发出去就落在第三方 IM 的聊天记录里，比本地日志难收回得多。
   `mask()` 折叠凭据、`password=`/`token=` 的值与长哈希串，
   但**主机名、服务名、路径、退出码这些运维真正要用的信息原样保留**。
   两个方向的代价不对称：默认开只是通知里少一段（还能去审批单看原文），
   默认关则是凭据进了别人的服务器 —— 所以默认开。

## 5. 排障：怎么确认"通知到底通没通"

| 看哪 | 能看到什么 |
|---|---|
| `GET /incidents` | `notify.enabled` / `notify.channels` / `notify.mask`：当前是开是关、发去哪 |
| `GET /incidents/{id}` | `notifications` 数组：每一次投递的渠道、成败、错误（**失败不许谎报成功**） |
| `logs/audit.jsonl` | `notify.sent` / `notify.failed` / `notify.deduped` 三类事件，带 key 与逐渠道结果 |
| `GET /incidents` 的 `aggregate` | 当前是 `aggregate` 还是 `legacy-exact`（免得以为开了聚合、其实配置里关着） |

**没收到通知时的排查顺序**：

1. `NOTIFY_CHANNELS` 是不是空的？（空 = 完全不出站，这是默认值）
2. 渠道名拼错了？（`dingding` / `lark` / `wechat` 是高频拼错，会打印明确警告并跳过）
3. 看 `notifications` 里的 `error`：签名错误、关键词不匹配、限流都在里面
4. 看是不是被去重了（`NOTIFY_MIN_INTERVAL` 内同一 key 只发一次；审计里记 `notify.deduped`）

## 6. 已知边界（不藏）

| 边界 | 说明 |
|---|---|
| **去重与频控是进程内内存态** | 与限流层同一个取舍：单进程（`--workers 1`）下准确，多实例要换 Redis |
| **事件表内存随历史增长** | `_load` 是 O(全部历史)；事件是审计物，截断会让历史查不到，留给运维侧轮转（`logs/incidents.jsonl`） |
| **`ALERT_ASYNC` 已实现** | `=1` 时接口**立刻**返回 `{"async": true, "accepted": N}`，诊断在后台任务里跑（结论去 `/incidents` 查）。默认 0 = 同步，响应里直接带结论。★ **进程若在后台任务跑完前退出，这次诊断就丢了**（没有持久队列 —— 单进程 + 不加依赖是既定取舍），所以审计里留了 `alert.accepted` 可对账，事件会停在 `open` 而不会假装诊断过 |
| **真实钉钉/飞书机器人未实测** | 加签算法有固定密钥+固定时间戳的确定性用例，但没有服务端回验。**首次接入真机器人时先看 `errcode`/`code`** —— HTTP 200 会掩盖问题 |
| **`mask()` 不覆盖 PII** | 只覆盖凭据类（`sk-`、`Bearer`、`password=`、长哈希）。身份证/手机号等不在范围内：运维文本里不是主要风险，且误伤面很大 |
| **跑一次自检会在 `/incidents` 留一条事件** | 与 trace 同理（`/webhook/alert` 会被探一次）。要清干净就删 `logs/incidents.jsonl` |
