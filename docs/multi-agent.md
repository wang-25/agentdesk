## 第 0 章｜先说清楚：拆了到底多得到什么

多 Agent 最常见的批评是"为了拆而拆，还多花几次调用"。**这个批评大部分时候是对的。**

所以先讲收益，而且是能验证的收益。

### 四条收益

| 收益 | 具体表现 | 怎么验证 |
|---|---|---|
| **1. 上下文隔离** | 一个 Agent 跑久了，对话历史里会混进日志、命令输出、文档片段，全堆在一个上下文里互相干扰。拆开之后每个 Agent 只装自己那类数据 | 工具执行 Agent 的上下文里**没有**文档片段；知识检索 Agent 的上下文里**没有**命令输出 |
| **2. 可单独评测** | 意图路由和结果校验**不调工具**，输入输出都是结构化 JSON，有标准答案 | `scripts/eval_specialists.py` 算出**逐字段准确率**（见第 4 章） |
| **3. 权限最小化** | 工具执行 Agent 的 schema 清单里**根本没有** `search_knowledge` | `tool_names=DIAGNOSE_TOOLS`，5 个工具，实测可查 |
| **4. 可换不同档次的模型** | 意图分类这种简单活可以派给便宜的小模型，只有诊断推理需要大模型 | 目前没换，但结构上已经支持（各 Agent 独立调 `chat_step`） |

**第 3 条的实现方式值得单独强调**：

```
❌ 在提示词里写"请不要查知识库"      → 这只是请求，模型可以不理会
✅ 从工具清单里把 search_knowledge 去掉 → 这是约束，它连这个工具长什么样都不知道
```

> **能用结构约束的，就不要靠提示词请求。** 这句话在 Agent 工程里反复成立 ——
> 后面"不需要查现场就走纯推理模式"用的是同一招（工具清单给空列表）。

### 三条代价（也必须说）

| 代价 | 具体表现 |
|---|---|
| **多几次模型调用** | 一次完整流程至少 4 次（意图 + 诊断 + 校验 + 可能的知识检索），实测 5 次左右。单 Agent 是 2-3 次 |
| **链路变长，排障变难** | 出错时你不知道是哪个 Agent 的锅。所以必须有 `node_log`（每一步的耗时与摘要） |
| **Supervisor 的决策逻辑本身是新的 bug 来源** | 本次就踩到两次（见第 5 章） |

**结论：拆分的门槛是"你有没有需要被单独评测、或者需要隔离上下文的部件"。**
有就拆，没有就别拆。这个项目里这两条都成立 —— 所以拆是对的。

## 第 1 章｜架构

```
                      START
                        │
                ┌───────▼────────┐
                │   supervisor   │  只做决策，不干活
                │  （规则版）     │  每条决策都记下理由
                └───────┬────────┘
        ┌───────┬───────┼────────┬────────┬────────┐
        ▼       ▼       ▼        ▼        ▼        ▼
     intent  knowledge diagnose  reason  verify  finalize
        │       │       │        │        │        │
        └───────┴───────┴────────┴────────┴────────┘
                        │  每个专业 Agent 干完都回到 supervisor
                        ▼
                       END
```

**4 个 Agent，7 个节点。** 节点比 Agent 多一个是正常的：

| Agent（职责） | 节点 | 有工具吗 | 干什么 |
|---|---|---|---|
| **意图路由** | `intent` | 无 | 把一句人话压成结构化标签 |
| **知识检索** | `knowledge` | `search_knowledge` | 查历史故障经验 |
| **工具执行** | `diagnose` / `reason` | 5 个运维工具 / **空** | 查现场 / 纯推理 |
| **结果校验** | `verify` | 无 | 检查结论站不站得住 |
| — | `finalize` | 无 | 把四家的产出拼成最终回答 |

> **`diagnose` 和 `reason` 是同一个 Agent 的两种模式**，共用一份实现
> （`specialists.py` 的 `diagnose()`）。
>
> 为什么需要"纯推理"模式：「explain」类问题（比如"为什么清理日志要用 truncate"）
> 根本不需要查机器。硬要它去查一轮，既浪费钱又可能查出一堆无关数据干扰回答。
>
> **Agent 是"职责"，节点是"执行方式"** —— 同一个职责有不同的执行方式，
> 就多一个节点。这不是拆得更细，是同一个 Agent 的两种工作状态。

## 第 2 章｜三个必须想清楚的设计问题

### 问题一：Supervisor 用规则决策，还是让模型决策？

**两种都能做，我选了规则。**

| 规则决策 | 模型决策 |
|---|---|
| 可预测、可复现、零额外成本 | 灵活，能处理没预想到的路径 |
| 出错时能一眼看出是哪条规则错了 | 出错时你不知道它"为什么"这么选 |
| 容易测（给状态，断言下一个节点） | 不容易测（要造状态还得看运气） |

关键判断：**这套流程的步骤是确定的。** 意图 → 知识 → 诊断 → 校验 → 汇总，
这个骨架不会因为问题内容而变。变化的只有"要不要查知识库""查现场还是纯推理"——
而这两件事**由意图路由的结果驱动**。

> **用模型去决定一个已经确定的事情，只会引入不确定性，不会带来能力。**

什么时候该换成模型决策？出现真正需要动态规划的场景：
并行派给多个 Agent、任务可以递归分解、或者步骤数取决于运行时发现的情况。
那时候再换。

**决策逻辑**（`supervisor.py` 的 `make_supervisor_node`）：

```
1. 还没做意图分类              → intent
2. needs_knowledge 且还没查     → knowledge
3. 还没跑诊断（按意图选模式）    → diagnose / reason
4. 还没校验                    → verify
5. 校验没过且还有重试额度        → 回到诊断（retries += 1）
6. 其他                        → finalize
```

### ★ 一个容易被忽略的实现细节：Supervisor 是节点，不是条件边

「按状态决定下一步」这件事，LangGraph 里用 `add_conditional_edges` 一个函数就能做，
不需要单独的节点。**但我做成了节点。** 为什么？

因为**决策本身要可观测**：

```python
{
  "next_step": "knowledge",
  "supervisor_reason": "意图标注 needs_knowledge=true（依据：报告了具体异常现象（慢、502），需查原因）",
}
```

实测轨迹里的真实样子：

```
✓ supervisor      0ms  → intent｜先做意图分类，才能决定后续要不要查资料/查现场
✓ supervisor      0ms  → knowledge｜意图标注 needs_knowledge=true（依据：报告具体异常...）
✓ supervisor      0ms  → diagnose｜需要现场数据
✓ supervisor      0ms  → verify｜结论出来了，先校验再交给用户
✓ supervisor      0ms  → finalize｜校验通过，汇总输出
```

**「它为什么走这条分支」永远是可回答的。**
如果决策逻辑藏在一个匿名条件边函数里，这段信息就丢了 ——
出问题时你只能看到"走了这条路"，看不到"为什么"。

> **把决策做成显式的、带理由的产物，本身就是可观测性的一部分。**

### 问题二：Supervisor 和「意图路由 Agent」重复吗？

**不重复 —— 它只是看起来像两件事在干同一件事。**

它们在不同的层：

| | Supervisor | 意图路由 Agent |
|---|---|---|
| 管什么 | **编排** | **语义** |
| 看什么 | 已经做过哪几步、还差哪几步、失败了要不要重来 | 这是诊断还是咨询、涉及哪台机器、要不要查资料 |
| 输入 | 流程状态（`visited` / `retries` / `verdict`） | 用户那句话 |
| 输出 | 下一个节点名 | 结构化标签 |

**为什么值得分成两个？因为职责混在一起的代价是可测性。**
意图分类可以单独拿出来算准确率（第 4 章实测 90%），
而如果分类逻辑埋在 Supervisor 的决策里，你只能端到端跑一遍才知道准不准。

### 问题三：校验不通过怎么办？

回到工具执行 Agent 重来，但要带两样东西 —— **缺一样，"重试"就退化成"重来一遍"**：

| 带什么 | 为什么 |
|---|---|
| **上一次的具体问题** | 知道要改什么。不然等于期待"运气不一样" |
| **上一次已经查到的数据** | 知道不用再查什么。**这条是踩过坑才加的**（见第 5 章坑三） |

重来次数有上限（`max_retries`，默认 1）。到顶了就带着"未通过"的标记出结论 ——
**不通过也要给出结论，只是明确告诉你它没通过。**
悄无声息地放弃，和明确标记失败，是完全不同的两件事。

## 第 3 章｜★ 校验 Agent：这一章最值得看

### 3.1 为什么不能只让模型"再检查一遍"

让模型自检有一个根本问题：

> **它检查的是同一批信息，用的是同一个脑子。**
> 它编错了，再问一遍它多半还是觉得没错。

这叫"自证清白"，说服力很低。而且它会给出非常自信的"我看过了，没问题"。

### 3.2 正确做法：能规则化的用规则，规则查不了的才用模型

```
规则能查的（确定性强、可复现、零成本、不会产生幻觉）：
    · 结论里的数字能不能在证据里找到出处        ← 数值溯源
    · 有没有越权声明（"我已经清理了…"）
    · 有没有任何证据就下了结论
    · 结论是不是空的

只有规则查不了的，才交给模型：
    · 依据和根因之间的因果链站不站得住
    · 有没有把"相关"当成"因果"
    · 置信度标得合不合理
```

**而且顺序很重要：规则先跑。规则能判否就直接判否，一次模型调用都不花。**

```
实测（cache-01 那个用例）：
  结论里的数字无出处 → 规则直接判不通过，0ms，0 token，没进模型审核
  ← 对比：如果每次都先问模型，这一次就白花 1 秒和 1000+ token
```

这不是省钱，是**把确定性最强的判断放在最前面**。规则不会有幻觉，模型会有。

### 3.3 ★★ 校验器自己必须先被验证（而且一定会误报）

这是整个多 Agent 编排中最有价值的经验。

**第一版数值溯源的规则是对的，但作用范围划错了，于是连续产生三类误报：**

| 误报 | 例子 | 根本原因 | 修法 |
|---|---|---|---|
| ① 来源池漏了「用户的问题」 | 用户说"报 502"，结论里写 502 被判成"没出处" | **"证据"不等于"工具返回"**。凡是输入里已有的事实，都不是模型编造的 | 来源池加上用户问题 |
| ② 把「建议」里的参数当成"声称的数据" | `chmod 755`、`chown 999:999`、阈值 80% | **溯源只对"事实主张"有效，对"给出的建议"无效**。出现在「依据」里是断言"我查到了"，出现在「建议」里是断言"你应该用" | 只在「现象」+「依据」两段内溯源 |
| ③ 主机名里的数字 | `web-01`、`cache-01`、`/dev/vda1` | 那是**标识符的一部分，不是测量值** | 用否定环视只认独立出现的数字 |

**修完之后实测（正例反例都验过）**：

| 输入 | 期望 | 实际 |
|---|---|---|
| 依据里写"使用率 96%"（证据里有 96） | 通过 | ✅ 通过 |
| 依据里写"用户提到的 502" | 通过 | ✅ 通过 |
| 建议里写 `chmod 755 /var/log` | 通过 | ✅ 通过 |
| 依据里写"使用率 98%"（证据里是 96） | **发现** | ✅ 发现 |
| 写"我已经清理了 /var/log" | **发现** | ✅ 发现 |
| 模型没按段落格式输出 | 跳过并说明 | ✅ 跳过并说明 |

这些正反例现在跑在 `scripts/smoke_test.py` 里 —— **校验器自己也是被测对象**。

### 3.4 三条关于写校验器的经验

**一、写完校验器，先证明它会在异常状态下失败。**
一个"永远返回通过"的校验器比没有更糟 —— 它会给你虚假的安全感。
（这条原则在 MCP 的 schema 校验里也用过。）

**二、误报比漏报更消耗信任。**
一个总在报假警报的校验器，最后会被所有人忽略 —— 那它等于不存在。
所以遇到误报要**立刻修**，而不是"反正只是提示"。

**三、校验规则每加一层范围限定，就暴露出一类新的"正常但不该被检查"的东西。**
写第一版时就要有预期：**它一定会误报，靠真实数据一轮轮收窄。**
本次收窄了三轮。

## 第 4 章｜实测数据

### 4.1 意图路由 Agent 的准确率（可单独评测的兑现）

```bash
.venv\Scripts\python.exe scripts\eval_specialists.py
```

20 条标注用例，5 个字段逐项判定：

| 字段 | 准确率 | 对了/总数 |
|---|---|---|
| `task_type` | **100.0%** | 22/22 |
| `hosts` | **100.0%** | 21/21 |
| `services` | 85.7% | 6/7 |
| `needs_live_data` | **100.0%** | 22/22 |
| `needs_knowledge` | 87.5% | 7/8 |

**全字段全对率：90.9%（20/22）**　分难度：basic 8/9、edge 8/9、tricky 4/4
**需要二次修正的用例：0/22**（说明提示词写得够清楚，一次就到位）　平均 1051ms/条

> **为什么逐字段算，不只算"全对率"**
> 一个用例可能 5 个字段里对 4 个，"全对率"会把它和"全错"一视同仁。
> 逐字段看才知道**该优化哪个字段** —— 比如 `services` 只有 85.7%，
> 说明"模型会自己加戏补一个没提到的服务"（i02 那条：问 Redis，它把 docker 也加上了）。

### 4.2 ★ 第一次做评测就发现：错的有一半是我自己

第一轮跑出来 5 个失败，逐条分析之后：

| 用例 | 表面结论 | 分析后 | 处理 |
|---|---|---|---|
| i16 nginx/apache | services 错 | **是我标错了** —— 问题里明确提到了 apache，我只标了 nginx | 改标签 |
| i14 负载高不高 | task_type 错 | **两种答案都合理** —— 可以判 query（问状态）也可以判 diagnose（要判断+建议） | 加 `accept` 多解声明 |
| i20 vue3 语法 | task_type 错 | **判 explain 也说得通**（在问做法），我标 other 是想说"不属于运维范畴" | 加 `accept` |
| i02 Redis + docker | services 错 | **模型真的自己加戏了** | 保留为真实 miss |
| i18 502 一般什么原因 | needs_knowledge 错 | **模型真的判错了**（该查知识库但判了 false） | 保留为真实 miss |

**"错的有一半是我自己标错了"——这是真实评测工作的常态。**

教训有两条：
1. **标签错比模型错更常见，而且更隐蔽。** 看到失败要先怀疑标签，再怀疑模型。
2. **评测集必须区分「唯一正确答案」和「多种合理答案」。**
   对后一种硬钉一个标准答案，测的不是模型准不准，是你自己的判断偏好。
   所以加了 `accept` 字段显式声明多解 ——
   **不能靠"把标准答案改成模型给的"来让指标好看，那叫改测试，不叫改代码。**

### 4.3 多 Agent 完整流程实测

```bash
.venv\Scripts\python.exe -m app.agents.supervisor "web-01 上的网站访问很慢，有时报 502，帮我看下原因"
```

**顺利路径**（5 步，5 次工具调用）：

```
✓ supervisor   0ms  → intent｜先做意图分类
✓ intent    1069ms  diagnose｜主机 ['web-01']｜知识库 要｜尝试 1 次
✓ supervisor   0ms  → knowledge｜意图标注 needs_knowledge=true
✓ knowledge  487ms  检索词「访问慢 502 排查 处理」命中 3 条
✓ supervisor   0ms  → diagnose｜需要现场数据
✓ diagnose  5445ms  查现场｜1 轮 · 5 次工具调用｜1805 字
✓ supervisor   0ms  → verify｜结论出来了，先校验再交给用户
✓ verify     713ms  通过（model）｜日志直接给出 AOF 权限致命错误，排除项充分
✓ supervisor   0ms  → finalize｜校验通过，汇总输出
✓ finalize     0ms  1327 字

路径 intent → knowledge → diagnose → verify → finalize
token 4286 · 耗时 8768ms
```

**带重试的路径**（12 步）—— 校验没过时会真的回到诊断：

```
路径 intent → knowledge → diagnose → verify → diagnose → finalize
```

**最终回答的开头会自动带上编排层的产物**（这是单 Agent 模式给不出的信息）：

```
> 路由：diagnose｜主机 ['web-01']｜服务 未指定｜查知识库 是
> 判断依据：报告具体异常现象（慢、502），需查原因

**现象**：web-01 上 nginx 反代的上游 WordPress 容器响应超时导致 502/访问慢…
**依据**（均为工具返回数据）：…
**结论校验**：通过（model）｜依据与根因对应合理，置信度标注得当
```

## 第 5 章｜五个真实踩到的坑

### 坑一：悬空 tool_calls 导致 400（撞 max_steps 时）

```
HTTP 400: An assistant message with 'tool_calls' must be followed by
tool messages responding to each 'tool_call_id'
```

**根因**：协议要求 `tool_calls` 和 `role: tool` 的应答**成对出现**。
而路由是**在 agent 节点产出新 tool_calls 之后**才判断"步数用完了"：

```
agent 产出 3 个 tool_calls
  → 路由：steps 已 >= max_steps → 直接去 finalize
  → 那 3 个 tool_calls 永远没有人应答 → 服务端拒绝
```

**循环被掐断在了"半路"—— 正好掐在发出请求、还没收到结果的中间。**

**为什么手写版没这个问题**：手写版的结构是"先执行完这一轮所有工具调用，
再进入下一轮"，所以它停下来的时候最后一条消息一定是 tool 消息，天然成对。

**同一个逻辑，两种结构，一个天然避开，一个没有。**
这不是"框架不好"，而是提醒：**换实现方式时，协议约束要重新过一遍。**

**修法**：给没有执行的 tool_calls 补一条占位 tool 消息，内容说明
「已达工具调用上限，本次调用未执行」。

**为什么是"补占位"而不是"删掉"**：删掉也能绕过报错，但会丢掉"模型想查什么"这条信息。
补占位之后 —— **实测下来模型会诚实地说出来**：

```
**置信度说明**：以上为「可能」，不是「确定」。因为日志类证据完全缺失 ——
nginx error log 与 mariadb 日志的两次 tail_log 调用均因达到工具调用上限而未执行
（返回 skipped: true），所以无法确认 502 的具体上游错误…
```

**它主动把置信度从「确定」降到「可能」，并说清了缺什么。**
这就是"保住信息"和"消掉报错"的区别。

> **修 bug 时优先保住信息，而不是把报错消掉。**

### 坑二、三、四：数值溯源的三类误报

见第 3.3 节，这里不重复。**这三个坑的共同点是：规则本身没错，作用范围错了。**

### 坑五：★ "重试"退化成了"重来一遍"

**现象**：第一次跑到重试路径时，工具执行 Agent 第二次调用**把同样的工具又查了一遍**
（`check_disk` `check_load` `check_service` `list_containers`），
然后再次撞上工具调用上限 —— **真正缺的日志数据一次都没读到。**

**根因**：子 Agent 每次启动都是一个**全新的对话**。它不知道上一轮查过什么。

> **跨轮次的记忆缺失，是"重试"退化成"重来一遍"的根本原因。**

**修法**：重试时把"已经查过的数据摘要"一起传进去，并明确要求
"把有限的工具调用额度用在还没查过的数据上"。

**修完实测**：第二次重查只用了 3 次工具调用（原来 4-5 次），
而且轨迹里能看到标记 `第 1 次重查（已带上上轮数据）`。

**这个坑的普遍性**：任何"失败重试"的机制都要问一句 ——
**重试的时候，上一轮的状态有没有传过去？**
没有的话，它只是在重复，不是在重试。

## 第 7 章｜设计问答

### 7.1 为什么要拆成多个 Agent

> 四条能验证的收益：**上下文隔离**（每个 Agent 只装自己那类数据）、
> **可单独评测**（意图路由不调工具、有标准答案，我算出了逐字段准确率）、
> **权限最小化**（工具执行 Agent 的 schema 里根本没有 search_knowledge）、
> **可以换不同档次的模型**（简单分类用便宜模型）。
>
> 代价我也清楚：多几次调用、链路变长更难排障。
> **所以拆分的门槛是"有没有需要被单独评测或需要隔离上下文的部件"。**
> 有就拆，没有就别拆。

### 7.2 Supervisor 与意图路由 Agent 是否重复

> 不重复，在两层。**Supervisor 管编排** —— 已经做过哪几步、还差哪几步、
> 失败了要不要重来，看的是**流程状态**。**意图路由管语义** ——
> 这是诊断还是咨询、涉及哪台机器，看的是**问题内容**。
>
> 分开的理由是可测性：意图分类可以单独算准确率，我实测是 90%；
> 如果分类逻辑埋在 Supervisor 的决策里，只能端到端跑一遍才知道准不准。

### 7.3 Supervisor 为什么用规则决策

> 规则。因为**这套流程的步骤是确定的** —— 意图 → 知识 → 诊断 → 校验 → 汇总，
> 这个骨架不会因为问题内容而变，变的只有"要不要查知识库""查现场还是纯推理"，
> 而这两个由意图标签驱动。
>
> **用模型去决定一个已经确定的事情，只会引入不确定性，不会带来能力。**
> 规则还能一眼看出是哪条规则错了，也容易测。
> 等出现真正需要动态规划的场景（并行派发、任务递归分解），再换模型决策。

### 7.4 校验为什么不能只让模型自检

> 因为**它检查的是同一批信息、用的是同一个脑子**。它编错了，
> 再问一遍它多半还是觉得没错 —— 这叫自证清白。
>
> 我的做法是**能规则化的用规则，规则查不了的才用模型**：
> 数字有没有出处、有没有越权声明、有没有证据就下结论，这些用规则；
> 因果链站不站得住、置信度标得合不合理，这些才交给模型。
>
> **而且规则先跑** —— 规则能判否就直接判否，一次模型调用都不花。
> 规则不会有幻觉，模型会有。

### 7.5 校验规则的误报问题

> 会，而且我踩了三轮。第一版规则是对的，但**作用范围划错了**：
>
> 1. 来源池漏了「用户的问题」—— 用户说"报 502"，结论里写 502 被判成没出处。
>    **「证据」不等于「工具返回」，输入里已有的事实不是模型编造的。**
> 2. 把「建议」里的参数当成声称的数据 —— `chmod 755`、阈值 80% 被判成没出处。
>    **溯源只对"事实主张"有效，对"给出的建议"无效。** 所以我把作用范围收窄到
>    「现象」和「依据」两段。
> 3. 主机名里的数字 —— `web-01` 的 01 被当成测量值。用否定环视只认独立出现的数字。
>
> 收窄完之后，我用正例反例各测了一遍：
> 有出处的数字要过、来自用户问题的要过、建议里的参数要过、
> **编造的数字要抓到**、越权声明要抓到。这 6 个正反例现在跑在自检脚本里。
>
> **一个"永远返回通过"的校验器比没有更糟** —— 它会给你虚假的安全感。

### 7.6 评测中的标签错误

> 最大的坑是：**第一轮跑出来 5 个失败，逐条分析之后发现有一半是我自己标错了标签。**
>
> 比如"nginx 和 apache 有什么区别"，我标 services 只有 nginx ——
> **问题里明明写了 apache，是我漏了。** 还有两条是"多种答案都合理"
> （"负载是不是太高了"可以判 query 也可以判 diagnose），硬钉一个然后判模型错，
> 测的其实是**我自己的判断偏好**，不是模型准不准。
>
> 所以我做了两件事：修正标错的标签；给评测集加 `accept` 字段显式声明多解。
> **不能靠"把标准答案改成模型给的"来让指标好看 —— 那叫改测试，不叫改代码。**
>
> 最终的诚实数字是：20 条用例，全字段全对率 90%，task_type 和 hosts 都是 100%，
> services 只有 80%（模型会自己加戏补一个没提到的服务），
> 剩下 2 个是模型的真实 miss。
