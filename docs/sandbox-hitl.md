# Docker 沙箱执行 + Human-in-the-Loop

## 一句话

早先做过 6 个**只读**工具，当时留了半句话：**"模型永远不执行任何东西，
它只是提出请求，真正决定执不执行的是你的代码。"**

这里补上另一半：**当"执行"真的发生之后，谁来兜底。**

答案分三层：沙箱是**边界**（限定最坏能坏到哪），审批是**授权**
（谁点的头），审计是**证据**（出了事查得到）。三个缺一个，Agent
就不该被允许碰生产环境。

---

## 一、为什么"只做沙箱"或"只做审批"都不够

| 做法 | 会出什么问题 |
|---|---|
| 只做沙箱，不做审批 | 隔离层被绕过时，你连"它被绕过"都不知道。而且沙箱解决不了"该不该做"，只解决"做坏了别扩散" |
| 只做审批，不做沙箱 | 人点同意之后，命令在一个**没有任何限制**的环境里跑。审批只回答"谁负责"，不回答"最坏能坏到哪" |
| 两个都做 | 隔离限定破坏范围的上界，审批限定变更的归属 |

## 二、三层各干了什么

### 1. 沙箱（`app/sandbox/`）

```
policy.py     准入规则：白名单 + 参数级校验 + 三维决策（只判断，不执行）
executor.py   执行：容器通道 / 主机通道 / 仿真通道
approvals.py  审批单：生命周期、指纹绑定、单次消费、追加日志
```

**核心是 `policy.py` —— 它回答"这条命令允不允许跑"。**

- **白名单，不是黑名单**：`rm -rf /` 列不完（`rm -fr /`、`find / -delete`、
  `dd`、`mkfs`、`> /dev/sda`……）。所以只放行登记过的 13 条命令，
  不在表里 = 不许跑。
- **按子命令管，不是按可执行文件管**：`systemctl` 不能整体放行
  （否则 `systemctl disable firewalld` 也进来了），必须拆成
  `is-active`（只读）/ `status`（只读）/ `restart`（需审批）三条，
  共用一个 bin、三个不同决策。
- **路径白名单**：`cat /etc/shadow`、`tail -n 5 ../../etc/passwd`、
  `truncate -s 0 /etc/passwd` 都要挡。路径必须落在登记过的目录里，
  而且**写操作只允许 `.log` 文件**。

**三维决策：**

| 决策 | 含义 | 例子 |
|---|---|---|
| `allow` | 只读诊断，直接执行 | `df -h`、`tail -n 20 …` |
| `needs_approval` | 可逆写，必须人工确认 | `systemctl restart nginx`、`truncate -s 0 …` |
| `deny` | 高危，策略层面封死，谁确认都不做 | `rm -rf`、`dd`、`chmod` |

### 2. 执行通道（`executor.py`）

**"把命令放进 docker run"不等于安全。** 这是本天最想讲清的一个判断：

- 写文件的操作 → **容器通道**：文件系统只读、无网络、掉全部 capability、
  非 root、内存 CPU 进程数封顶。**真隔离。**
- 管服务的操作 → **主机通道**：`systemctl` / `docker restart` 必须碰到
  宿主机的 systemd 和 docker daemon，容器里根本够不着。**没有容器隔离**，
  靠白名单 + 审批 + 审计兜底。

**判据不是"读还是写"，是"隔离值不值得付它的成本"：**

> `du` 改不了任何东西，隔离对它没有额外收益，反而挂载方案会限制它能看的
> 范围（挂 `/` 太重、只挂 `/var/log` 又不够用）。所以 `du` 走主机通道。
> `truncate` 会改文件，只挂 `/var/log` 就够用且刚好封住了范围。所以走容器。

**隔离不是越多越好，是"刚刚够用"最好。**

### 3. 审批单（`approvals.py`）

三个刻意设计：

- **批准必须填审批人**：一张没有审批人的审批单，等于没有审批。
  事故复盘时"系统批准的"不是能交差的回答。
- **批准和执行分成两个动作**：因为"同意这么做"和"现在就做"是两件事，
  拧在一起就没法表达"同意但等维护窗口再执行"。
- **指纹绑定（防 TOCTOU）**：审批时记下"这条命令 + 通道 + 挂载"的哈希，
  执行时重算比对。不一致就拒绝。**批准的必须是执行的那一条。**

**审批单用追加 JSONL 日志持久化**，状态靠"折叠日志"得到 —— 和 audit.jsonl
同一个模式：追加是原子的（写到一半断电前面几行仍完整）、可审计（每次状态
变化都留痕）、可重建（删掉内存重启后一模一样）。

## 三、一次写操作的完整链路

```
模型想执行 truncate -s 0 /var/log/nginx/error.log
  ↓ policy.decide()
    命中 truncate 规则 → needs_approval
    路径在 /var/log 下且是 .log → 通过
    算指纹，挂 /var/log 为 rw（容器通道）
  ↓ approvals.create()
    生成 ap-xxxxxxxx，状态 pending，落盘
  ↓ 工具把审批单作为「观察结果」返回给模型
    模型据此回答"已提交审批，等待人工确认"（而不是"已清理"）
  ↓ 人：GET /approvals?status=pending → 看到它
        POST /approvals/{id}/approve {by:"张三"}
        POST /approvals/{id}/execute
  ↓ 执行时三道校验：
    ① 状态必须 approved（挡住"没批就执行"）
    ② 只能消费一次（挡住"一次批准执行一百次"）
    ③ 指纹必须一致（挡住 TOCTOU）
  ↓ executor.run() → 一次性容器：无网络、根只读、掉全部 capability
  ↓ 结果写审计；审批单 → consumed（不能再执行第二次）
```

## 四、Agent 侧：诊断与处置分离

`run_command` 是第 7 个工具，也是唯一 `risk=high` 的工具。但它**没有**加进
诊断 Agent 的工具集 —— 而是拆出了第 5 个专业 Agent：**处置 Agent**。

**为什么不能直接给诊断 Agent 加个工具：**

> 诊断是只读的，错了的代价是"结论不准，人一眼能看出来"；
> 处置会改系统，错了的代价是"服务中断、数据丢失"。
> 把两种权限混在一个 Agent 手里，就等于为了让它可以重启服务，
> 顺带把"随时能重启服务"的能力给了它做诊断的每一步。
> **权限一旦给出去，就没有"只在这一步有效"这回事。**

于是处置 Agent 的工具集只有 `run_command` 一个，而诊断 Agent 的工具集里
**根本没有 run_command 这个 schema** —— 即使诊断 Agent 被注入攻破，它也
做不了任何改动。这是结构上的隔离，不是提示词上的约定。

**外加一道安全规则：结论没过校验，就不许据此动手。**

处置是"基于诊断结论"的。校验 Agent 说结论站不住，那它的建议同样可疑。
所以 Supervisor 只有在 `verdict.pass` 为真时才派发处置 Agent；
结论没过校验时明确输出"**未执行任何处置动作**"。

## 五、fail-closed：沙箱不可用时怎么办

这是本天最容易搞反、也最重要的一条。

| | 行为 | 后果 |
|---|---|---|
| fail-open（错） | 沙箱不可用 → 直接执行 | 隔离失效的那一刻恰好是最危险的时候，而且全程无信号告诉你隔离没了 |
| **fail-closed（本项目）** | 沙箱不可用 → 拒绝执行，返回明确的"未执行" | 安全属性不会因环境变化静默丢失 |

真实事故里，"降级执行"比"拒绝执行"危险得多，因为**没人会注意到降级**。

所以 `auto` 模式探测不到 Docker 时，**默认落到 mock（仿真），绝不悄悄降级成
subprocess 无隔离执行**。要无隔离执行必须显式设 `SANDBOX_BACKEND=subprocess`，
启动时还会打警告。

## 六、实测数据

**意图路由 → 处置链路**（engine=supervisor）：

```
问题：web-01 上 nginx 的日志把磁盘写满了，帮我把旧日志清理掉
路径：intent → knowledge → diagnose → verify → remediate → finalize
处置：提交审批 truncate -s 0 /var/log/nginx/access.log（通道=container，真隔离）
```

**审批单生命周期**（HTTP 实测）：

| 动作 | 结果 |
|---|---|
| 批准（by=值班工程师-张三） | 200，`status=approved` |
| 执行 | 200，`status=consumed`，`ok=true` |
| 再执行（防重放） | **409**，`状态是 consumed，不能重复执行` |
| 再批准（已消费） | **409**，`不能再批准（只有 pending 可以批准）` |
| 批准但不填审批人 | **422**（`by` 必填） |

**★ 装上 Docker 之后的真实验证（补做，这是最终结论）**

沙箱隔离参数逐项实测：

| 隔离项 | 验证方式 | 结果 |
|---|---|---|
| 非 root | `id -u` | `65534` ✓ |
| 根文件系统只读 | `touch /etc/x` | `Read-only file system` ✓ |
| tmpfs 可写 | `touch /tmp/x` | 成功 ✓ |
| 无网络 | `ping 1.1.1.1` | `Network unreachable` ✓ |
| 内存封顶 | 读 cgroup `memory.max` | `134217728`（128MB）✓ |

完整 HITL 端到端（真实容器执行）：

```
造真实日志文件（2 行）
  → Agent 提交 run_command truncate -s 0 /var/log/nginx/access.log
  → 决策 needs_approval，生成审批单，**不执行**
  → 人工批准（by=ops-drill）
  → 指纹比对一致 → 一次性容器执行（backend=docker, isolated=True, exit=0）
  → 验证文件：0 字节 ✓
```

**过程中被拦下一次 Permission denied**（root 属主文件 + 容器以 nobody 运行）——
这不是故障，是"非 root 运行"在做它该做的事，也顺手演示了真实生产里
最常见的权限问题。修好文件属主后同一条链路完整跑通。

**九层自检**：沙箱 5/5、审批 3/3、观测 9/9，其余层全绿。

### 6.6 真容器隔离：逐条实测（Windows + Docker Desktop，2026-09-29）

Docker 运行中时 `/sandbox` 报 `backend=docker`、`isolated=true`。
下面是**逐条打点**的结果 —— 用项目自己的 `executor.docker_argv()` 起容器，
所以验的是真实参数，不是另抄一份：

| 声明的限制 | 容器内实测输出 | 结论 |
|---|---|---|
| 非 root | `uid=65534(nobody) gid=65534(nobody)` | ✅ |
| 根文件系统只读 | `touch /pwned` → `Read-only file system`；`mount` 显示 `overlay on / (ro,…)` | ✅ |
| /tmp 能写不能执行 | 写文件成功；执行 `sh /tmp/x.sh` → `Permission denied`；`tmpfs on /tmp (rw,nosuid,nodev,noexec,size=16384k)` | ✅ |
| capability 全掉 | `CapPrm / CapEff / CapBnd` 全是 `0000000000000000` | ✅ |
| 内存封顶 | `cat /sys/fs/cgroup/memory.max` → `134217728`（=128MB） | ✅ |
| CPU 封顶 | `cpu.max` → `50000 100000`（=0.5 核） | ✅ |
| 进程数封顶 | `pids.max` → `64` | ✅ |
| 不能提权 | `su -` → `must be suid to work properly` | ✅ |
| **无网络** | 只有 `lo`；默认路由 **0 条**；TCP 连 `1.1.1.1:53`、`8.8.8.8:53`、HTTP 取 example.com **全部失败（退出码 1）** | ✅ |
| **写操作真落到宿主机** | 挂一个 5000 字节的宿主文件 → 容器内 `truncate -s 0` → 宿主上变成 **0 字节** | ✅ |

> **这不是"参数写对了"的证明，是"参数真的生效了"的证明。**
> 上面任何一条只在代码里写着、没在容器里 `cat` 出来过，都不算验证过 ——
> 本项目的审计报告当初正是卡在这一步：「真容器执行这条路我测不了」。

**通道差异（容易被误读）**：只读命令走**宿主面子进程**，写命令才走**一次性容器** ——

| 命令 | 通道 | 含义 |
|---|---|---|
| `df -h` / `free -m` | `host` | 直接在宿主上跑，`isolated=False`（只读、不拼 shell、argv 走白名单） |
| `truncate -s 0 <日志>` | `container` | 一次性容器，`isolated=True` |

所以自检里看到「后端 docker 但 `isolated=False`」是正常的 —— 那条探的是只读通道。
**"后端是 docker"和"这一条命令跑在容器里"是两件事。**

**已知前提（是取舍，不是 bug）**：容器以 `nobody` 运行，因此「挂载出来的目录必须对它可写」。
在 Windows + Docker Desktop 上直接跑真实的 `truncate /var/log/nginx/error.log` 会得到
`open: Permission denied` —— 该目录在宿主上不存在、由 Docker 新建，属主不匹配。
这与 `docs/observability.md` 里记的是同一件事：**`Permission denied` 正是"非 root 运行"
在做它该做的事**。要在真机上用这条路，需让目标日志目录对 `nobody`（或等价 uid）可写。

## 七、踩到的坑（比结论更值钱）

**一、白名单规则静默失效**

第一版 systemctl / docker 的 validator 按"纯参数"写，但实际传进来的是
"子命令 + 参数"。结果 12 条规则里有 5 条**从来没生效过**，而且不报错 ——
文档里写着支持 `systemctl restart`，实际永远是"参数形式不被允许"。

> **"存在但从不被触发"的代码，比不存在的代码危险。** 不存在的你会去补；
> 永远不触发的，你以为它已经在保护你了。

解法：加 `_sub()` 助手统一"剥离子命令"，并且**用每条规则自己的 example 去
跑一遍**（现在固化在自检脚本里，13/13）。

**二、白名单混进一个"匹配一切"的值**

`_INSPECT_DIRS` 里放了 `/`，而校验用 `startswith(d + "/")` —— 对 `/` 而言
`d.rstrip("/")` 是空串，条件退化成 `startswith("/")`，**任何绝对路径都成立**，
白名单等于没写，`du -sh /root` 被放行了。

> 表里混进一个"通配一切"的值，它不报错、不告警，只是让整张表形同虚设。
> 从代码上看，那一行还特别像"允许根目录"这样一个合理的配置。

解法：`/` 单独判断，不进白名单表。

**三、mock 数据自相矛盾，被 Agent 逮住了**

我的 mock 里 `/` 96% 满、`/var` 35%，而 nginx 日志在 `/var/log`（属于 `/var`）——
**清理日志根本不会释放根分区空间**。处置 Agent 读出了这个矛盾，明确拒绝清理，
还写了"不要批准清理 /var/log/nginx —— 它解决不了根分区满的问题"。

这其实说明"处置必须基于诊断依据"这条约束是有效的。但也提醒：

> **mock 数据也要过一致性检查。** 数据里凡是"能被推理出来的关系"，
> 都要和真实场景自洽，否则要么误导 Agent，要么暴露设计漏洞。

（已把第二块盘改成 `/data`，让"根分区满 → nginx 写不了日志 → 502"的因果链成立。）

**四、mock 后端缺数据，Agent 拿不到证据就不动手**

第一版 mock 对 `du` 只返回占位文案，没有数字。处置 Agent 想确认"日志是不是主因"
时拿不到证据，于是**拒绝提交清理动作**。拒绝是对的，但根因是 mock 数据不完整。

> 想让 Agent 在测试环境里走通生产会发生的流程，mock 数据就得给够信息。

（补齐了 `du` 的仿真数值后，处置 Agent 顺利提交了审批单。）

**五、审批的"批准"和"执行"用了 `by=张三` 的中文，在 curl 命令行直传时被编码搞坏**

这不是新坑 —— 早先就说过"中文 JSON 别在命令行直传，用文件或 httpx"。
这里再次应验，测试脚本里所有审批调用都改用了 httpx。

## 八、设计问答

**为什么只做沙箱不够，还要加人工确认**

因为沙箱回答"最坏能坏到哪"，不回答"该不该做"。一个正确但需要授权的操作
（重启生产服务），隔离再严也挡不住"执行了"这件事本身。审批回答"谁负责"，
这是事故复盘时要交的答案。

**把命令放进 docker run 就安全了吗**

对 `df -h` 这种命令，放进容器你得到的是**容器的磁盘视图**，不是宿主机的；
对 `systemctl restart`，容器里的 systemd 和宿主机是两个世界，根本够不着。
所以"放容器"不是万能的，要先分清"对文件做的事"和"对服务做的事"。

**怎么防"一次批准执行一百次"**

审批单是状态机，`approved → consumed` 只能走一次，`consumed` 是终态。
第二条 consume 会撞在状态校验上。这是审批系统要防的头号漏洞（重放）。

**沙箱不可用了怎么办**

fail-closed：拒绝执行，不降级。因为"降级执行"比"拒绝执行"危险得多，
而且没人会注意到降级 —— 安全属性会在环境变化时静默丢失。

## 九、怎么用

```bash
# 看沙箱状态 + 命令白名单（不花钱）
curl http://127.0.0.1:8000/sandbox

# 走一遍完整闭环（起服务后）
# 1. Agent 生成审批单
.venv\Scripts\python.exe -m app.agents.supervisor "web-01 磁盘满，把 nginx 日志清了"
# 2. 看待审批
curl "http://127.0.0.1:8000/approvals?status=pending"
# 3. 批准 + 执行（用 httpx 或 /docs 页面，别在 curl 里直传中文）
# 4. 沙箱层自检（离线）
.venv\Scripts\python.exe scripts\smoke_test.py
```

**切到真隔离**：装 Docker Desktop → `.env` 里 `SANDBOX_BACKEND=docker` →
`docker pull alpine:3.20` → 重跑。之后 `truncate` 会真的在一次性容器里执行。
