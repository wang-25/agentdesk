## 0. 结论先说

现在这套界面**不是"不够漂亮"，是三件事同时不对**：

1. **定位不对**：首页是"渲染出来的 README"（单列居中、纯文字、无导航、无图标），
   而用户打开一个运维 Agent 期待的是一个**控制台**。
2. **有真 bug**：看板上的两张图表（成本分布条形图、执行时间线）**渲染出来是空的**。
3. **信息架构缺失**：5 个页面之间没有导航，没有全局状态，
   每个页面各带一份 34–53 行的 `<style>` 互相重复 —— 改一处要翻 3000 行。

而 **UI 代码占 `main.py` 的 49%**（1475 / 3039 行）。所以这件事不只是"美化"，
它同时也是**把主文件减半**的机会。

## 1. 现状证据（截图 + 代码核对）

### 1.1 已确认的渲染 bug（不是审美问题）

`.hbar .fill`（成本分布条形图）与 `.tl-fill`（执行时间线）的 CSS 是：

```css
.hbar .track { flex: 1 1 auto; height: 12px; overflow: hidden; }
.hbar .fill  { height: 100%; background: var(--accent); }   /* ← 不生效 */
```

`<span class="fill">` 是**行内元素**，而**行内元素的高度与宽度不生效**
（CSS 规范：height 只对非替换的行内元素之外适用）。
`.track` 因为自己是 flex 子项被块级化了，但 `.fill` 不是 —— 于是填充条高度为 0。
**结果：图表画出来了容器，数据条一条都看不见**（视觉分析独立报告了同一现象）。

> 修法：`.fill { display: block; }`（或把容器改成 flex）。
> 这类 bug 靠"看代码"很容易漏，靠**截图**一眼就能看见 —— 所以下面第 5 节把截图做成门禁。

## 3. 设计系统（唯一的 CSS 来源）

```css
:root{
  /* 中性阶 */
  --bg:#f7f8fa; --surface:#fff; --surface-2:#fbfcfd;
  --border:#e4e7ec; --border-strong:#d0d5dd;
  --text:#101828; --text-2:#475467; --text-3:#667085;
  /* 语义色 */
  --accent:#2563eb; --ok:#16a34a; --warn:#d97706; --err:#dc2626;
  /* 间距（4 的倍数）· 字号 · 圆角 · 阴影 */
  --s1:4px; --s2:8px; --s3:12px; --s4:16px; --s6:24px; --s8:32px;
  --fs-xs:12px; --fs-sm:13px; --fs-md:14px; --fs-lg:16px; --fs-xl:20px; --fs-2xl:24px;
  --r-ctl:6px; --r-card:10px; --r-pill:999px;
  --shadow-1:0 1px 2px rgba(16,24,40,.06);
  --shadow-2:0 4px 12px rgba(16,24,40,.08);
}
```

**规则（写进 CSS 注释，避免下次又走样）**

1. **数字一律右对齐 + `font-variant-numeric: tabular-nums`** —— 让列能对齐扫读
2. **货币按量级自适应精度**：`¥0` / `¥0.0004` / `¥12.34`；不把 0 显示成 `¥0.0000`
3. **指标口径解释不进正文**：一律 ⓘ 悬停 + 页脚折叠区（看板上那 100 字散文就是反例）
4. **空态、加载态、错误态是组件**，不是"什么都不显示"（`EmptyState` / `Skeleton` / `ErrorState`）
5. **对比度**：正文 ≥ 4.5:1；卡片用白底 + `--shadow-1` + `--border`（不再"白底压白底"）
6. 亮色为主（沿用 2026-09-30 的决定），但 token 结构**留好暗色的位置**，将来切换只改一处

**组件清单**（`app/web/components.py` 里各一个渲染函数）：
`Page/Shell` · `Card` · `StatCard` · `Table` · `Badge` · `Button(primary/ghost/danger)` ·
`Tooltip(ⓘ)` · `Timeline` · `BarList` · `EmptyState` · `Skeleton` · `Toast` · `Tabs`

## 4. 实现方案（关键取舍）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 继续内联在 `main.py`** | 零结构改动 | 已占 49%；每页重复样式；改一处翻 3000 行 | ✗ |
| **B. 抽到 `app/web/`：模板字符串 + `static/app.css`，零依赖无构建** | main.py 减半；视觉系统单一来源；改 CSS 可即时刷新调试；仍然零新依赖 | 仍是服务端渲染，没有组件框架的交互能力 | ✅ **推荐** |
| **C. 引入 React/Vue + Vite** | 交互与组件生态最强 | 新依赖 + 构建步骤 + 部署链变长；与"直接依赖仅 9 个、CI 有守卫"的项目原则直接冲突 | ✗ |

**B 的目录形态**

```
app/web/
├── __init__.py       # mount(app)：注册 5 个页面路由 + /static
├── layout.py         # 统一外壳：<head>、顶栏、页脚、注入 CSS/JS
├── components.py     # 上表那批组件，每个一个纯函数
├── pages/            # home.py · try_.py · dashboard.py · settings.py · view.py
└── static/app.css    # 设计系统的唯一实现（tokens + 组件）
```

- 静态文件用 FastAPI 自带的 `StaticFiles`（**零新依赖**）
- `main.py` 只留几行：`from app.web import mount` + `mount(app)`
- 页面数据仍从现有接口/函数取，**不动后端语义**（后端零改动是本方案的红线）

## 5. 验收标准（可复跑，不靠"我觉得好看"）

1. **图表非空**：`scripts/ui_check.py` 用无头 Chrome 截图 5 个页面，
   用 PIL 检查"条形图/时间线"区域的像素 —— **必须存在主色像素**（正是 1.1 那个 bug 的守门用例）
2. **样式单一来源**：5 个页面的 HTML 里**不再有页面级 `<style>`**
3. **`main.py` 行数**从 3039 降到 **< 1600**
4. **交互闭环**：`/try` 在提交前就有结果区骨架（断言该容器存在）；提交后四个分区（轨迹/结论/证据/成本）都出现
5. **导航与状态**：每页都有顶栏导航；状态点反映 `/healthz`（把它 stub 成失败态时，徽标变红）
6. **口径可追溯**：看板上每个数字都能点到它的定义（ⓘ），且"运行次数/表合计/扫描口径"三者有明确桥接说明
7. 既有 **1013 条用例全绿** + pytest 里补 5 个页面的 HTML 冒烟（200 + 关键选择器存在）
8. 六个门禁（pytest/ruff/mypy/security_check/mcp_check/检索基线）+ `smoke_test --strict` 全通
