|---|---|---|
| I-7 真语义检索 | "没有真语义"（听起来像功能缺失） | **可插拔 embedder 早就写好了**：`_encode_dashscope`（百炼 `text-embedding-v3`，1024 维，批量 10 条一条请求）就在 `app/rag/embedder.py`，`auto` 模式按 `DASHSCOPE_API_KEY` 是否存在自动选择。**代码链路是通的，缺的是 Key 与证据** |

1. **拿到 Key**（你有阿里云账号 —— `.env.example` 里那条注释就是给这个留的）
2. **给出证据**：同一套 `eval/qa_set.json` 上，`local-hash` 与 `dashscope` 的召回率差多少。
   **没有这个对比，"真语义更好"就只是一句话**，而这类"想当然更好"的改动恰恰最容易白花钱
3. **把检索质量本身做上去**：见下面的"混合检索"——它**不依赖 Key**，而且在运维语料上收益可能比换 embedder 更大

## 1. 四项现状核实（都是刚读代码确认的，非转述）

### I-6 会话与案例记忆 —— **完全没有**

`ChatRequest` 只有 `question` 一个字段（`app/main.py`），每次请求都是无状态的：
没有会话、没有历史、没有跨请求记忆。全仓搜 `session/conversation/memory` 只命中
事件表自己的 `history`（状态迁移记录）与一处演示字符串。

**"案例"也没有**：M2 建立的事件表里已经沉淀了"什么告警、怎么诊断的、最后怎么处理的"，
但这些数据**只用于展示，从未回流到诊断过程** —— 下一次同样的告警，Agent 还是从零开始。

### I-7 真语义检索 —— **后端就绪、混合检索已实现且已是默认、缺 Key 与"能分辨差异的评测集"**

★ **这一节最初写错了，必须纠正**：初稿把"混合检索（BM25 + RRF）"列为 M5a 要做的事。
读代码后发现 **它早就实现、早就接线、而且是默认模式**：

| | 实际情况 |
|---|---|
| BM25 / RRF | `app/rag/store.py` 里 `class BM25`、`rrf_fuse(rankings, k=60)` 都在，并有大量用例（`tests/test_rag_store.py`） |
| 接线 | `store.search(mode="hybrid")` 是**默认值**；`pipeline.retrieve/answer`、`/rag/ask`（`main.py:2828`）、`specialists.py`、`ops.py`、`run_eval.py` 全部默认走 hybrid |
| 模式对比 | `pipeline.evaluate()` 已经会跑 vector / bm25 / hybrid 三方对比并打印报告 |
| 基线 | `eval/baseline.json` **已经按模式**记录 recall（`vector.recall` / `bm25.recall` / `hybrid.recall`）并有容差门禁 |

**实跑一次的真实数字（`scripts/eval_baseline.py`，local-hash 后端）：**

```
  检索模式                            总体      词面型      语义型
  纯向量检索                        96.9%    96.2%   100.0%
  纯关键词(BM25)                  100.0%   100.0%   100.0%
  混合检索(向量+BM25+RRF)           100.0%   100.0%   100.0%
```

所以 I-7 真正缺的**只有两件**：

1. **Key**（你有 → M5d）：`_encode_dashscope`（百炼 `text-embedding-v3`，1024 维）代码就绪，
   `auto` 模式按 Key 是否存在自动切换。差的是"真语义到底好多少"这件事**没有证据**
2. **一个能分辨差异的评测集** —— 这是实跑数字暴露出的**更实质问题**：

   **BM25 单独就已经 100%**，混合也是 100%，纯向量 96.9%。也就是说
   **评测集饱和了**：它对"检索质量改进"已经没有分辨力 ——
   换真 embedding、加重排、调融合参数，**在这张表上都只会看到 100% → 100%**。
   于是任何"我让检索更好了"的说法都无法被证明，也无法被门禁保护。

   → 所以 M5a 里 I-7 的工作**不是写检索，而是把评测集做到能分辨**：
   补语义改写型（同义不同词）、精确标识陷阱（`wp-app` vs `wp-db`、`OOMKilled` vs CPU 高）、
   以及"文档里有答案但字面不重合"的负例。**这是 M5d 能有结论的前提** ——
   否则配了 Key 也只是换来一句"还是 100%"。

### I-8 全链路评测与墙钟预算 —— **评测有、预算没有、性能无门禁**

| | 现状 |
|---|---|
| 评测集 | `eval/qa_set.json`（32 条检索）、`eval/rag_eval_set.json`（40 条端到端）、`eval/intent_set.json`（22 条） |
| 评测脚本 | `scripts/run_eval.py`（六维度：4 规则 + 2 模型）、`eval_baseline.py`（检索门禁）、`eval_specialists.py`（意图路由） |
| **墙钟预算** | **完全没有**。supervisor 只有"校验重试次数上限"（`max_retries`），没有总时长/总成本上限 —— 一次卡住的运行会一直烧下去 |
| **性能门禁** | `eval/baseline.json` 只门禁**质量**指标。端到端**延迟与成本**没有任何基线，退化不会变红 |
| 逐节点耗时 | 有（`node_log` 里带 `elapsed_ms`），但只用于展示，没有汇总成 P50/P95 |

### I-9 处置剧本与回滚 —— **只有"命令清单"，没有剧本，也没有回滚**

`DIAGNOSE_PLAYBOOK` 是 `{服务名: [命令名, ...]}`（如 `["uptime", "df -h", "free -m"]`），
`DEFAULT_PLAYBOOK` 同理。它是**一堆只读命令的名字**：没有判定、没有分叉、
没有"做到哪一步算好"、**更没有回滚**。

## 2. 逐项方案

### I-6 会话与案例记忆

**A. 会话（可选，不传就是无状态 —— 这是兼容的关键）**

```
POST /chat   {question, session_id?}        # 不传 session_id 时行为与现在完全一致
GET  /sessions/{id}                          # 看这个会话的最近几轮
DELETE /sessions/{id}                        # 主动清掉
```

- 存储：`logs/sessions.jsonl` 追加 + 折叠（与事件/审批同一套路），**可审计、重启不丢**
- 上限：每会话保留最近 `SESSION_MAX_TURNS`（默认 10）轮；会话总数上限 + LRU 淘汰
- ★ **上下文要标注来源**：注入历史时明确写成"以下是**之前**的问答，仅供参考"，
  并带时间戳。理由：模型会把"上次的答案"当成"这次的事实"，而系统状态可能已经变了 ——
  这与本项目"不给模型喂未经标注的推测"的一贯做法一致

**B. 案例记忆（价值更高的一半）**

事件表里已经有"告警 → 诊断 → 处置 → 结论"，把它变成可召回的案例：

- 事件 `resolved` 时，把 `{告警指纹, 服务, 症状, 结论摘要, 处置动作, 耗时}` 追加到 `logs/cases.jsonl`
- 诊断时按**告警指纹 + 服务 + 症状关键词**召回最近 N 条相似案例，作为参考注入
- ★ **案例不是答案**：注入时明确标注"这是**历史**案例（{时间}），当初的处理未必适用于现在；
  请用当前机器上的实际数据重新判断"。**把历史结论当事实，是这个功能最大的风险**
- 复用已有事件表 → 不新增数据来源，也不要求用户改工作流

### I-7 混合检索 —— **已实现，M5a 只做"让评测集能分辨差异"**

见 §1 的纠正。M5a 在这一项上的实际工作：

- **不写检索代码**（BM25/RRF/混合/模式对比/按模式基线全都已有）
- **加固 `eval/qa_set.json`**：补三类能分辨的模式差异的用例
  1. **语义改写型**：问法与文档字面不重合，只有语义能命中（真 embedding 应当赢）
  2. **精确标识陷阱**：形近标识（`wp-app` vs `wp-db`）、命令名、错误码（BM25 应当赢）
  3. **干扰文档**：语料里有"看起来像答案"的段落，考排序而不只是召回
- **记录模式差异**：把加固后的三方对比数字写进文档；**若某类用例上 hybrid 没有赢，
  就如实写清楚是哪一类、为什么** —— 这才是后续调优的依据
- 重排（rerank）**留到 M5d**：现在评测集饱和，加了也证明不了它有用

### I-8 墙钟软预算 + 性能门禁

**预算**：`AGENT_BUDGET_SECONDS`（默认 `0` = 不限，行为不变）

到点后**不硬砍**，而是"软着陆"：
1. 停止**开新的**工具调用
2. 用已有信息生成结论，并在答案与审计里明确写"**因预算被截断**（已用 123s / 预算 120s，还有 2 个工具未执行）"
3. `stop_reason=budget`

★ 为什么不做硬超时：硬砍会把已经花掉的钱和已经查到的事实一起丢掉，
用户拿到的是一个没有结论的错误 —— **"以现有信息作答 + 如实说明被截断"严格优于"什么都没有"**。
这与 M3 里"审批记录必须回写真实结果"是同一条原则：**宁可报告残缺，也不要假装完整。**

**性能门禁**：`eval_baseline.py` 增加延迟/成本分位数（P50/P95 elapsed_ms、总 CNY），
写进 `eval/baseline.json`，容差同现有机制（超出即红）。
→ 从此"某次改动让每次问答慢了一倍"会**在 CI 里变红**，而不是靠人感觉。

### I-9 结构化处置剧本（**不做自动回滚**）

**先说边界**：项目核心边界是"写操作永不自动执行"。所以这一项**不做**自动执行、**不做**自动回滚。
做的是把"一份写死的命令清单"升级成**有判定与分叉的处置流程**：

```yaml
# 剧本：磁盘使用率过高
- id: check_disk
  run: df -h                    # 只读，走既有 policy 准入，自动执行
  expect: "使用率 > 90%"        # 判定
  on_pass: find_big_files
- id: find_big_files
  run: du -sh /var/log/*        # 只读
  on_pass: propose_cleanup
- id: propose_cleanup
  action: truncate_old_logs     # 写操作 → **开审批单，人工确认**
  rollback: ""                  # 声明"这一步不可回滚，请确认后再执行"
- id: verify
  run: df -h
  expect: "使用率 < 80%"
```

- **每一步都过既有准入与审批**，剧本只是把"该怎么处置"结构化、可审计、可复用
- **回滚是事前声明的**：能回滚的写操作必须写明反向步骤（同样是审批项）；
  不能回滚的**必须显式声明"不可回滚"** —— 执行前就让人知道，而不是事后现场想
- 剧本存 `plays/*.yaml`（纯文本、可 review、可进 git），加载时校验：
  命令必须命中 policy 白名单、必需步骤不能缺、写操作必须声明回滚或显式标注不可回滚
- 新增两个接口：`GET /plays`（列出）、`GET /plays/{name}`（看步骤与判定）

## 6. M5a 实施结果（**已完成**）

范围：I-8 墙钟软预算 + 性能门禁，以及 I-7 的"让评测集能分辨差异"。

| 项 | 结果 |
|---|---|
| **墙钟软预算** | `AGENT_BUDGET_SECONDS`（**默认 0 = 不限，行为与改动前一致**）。两套引擎都支持：手写版 `react.run(deadline=)`、框架版 `graph.run(deadline=)`；supervisor 解一次环境变量后随 state 传下去 |
| 到点后的姿态 | ① 不再开**新的**工具调用 ② 用已有信息收口（**仍花一次模型调用**把已知信息整理成结论 —— 比丢掉全部信息划算） ③ `stop_reason="budget"` + 专门的收口语（明写"还差什么没查""不要猜测没查过的数据"） ④ 指标 `agentdesk_agent_budget_exceeded_total{engine}` |
| **一个隐蔽的设计点** | 预算**只进 state，不进 `build_graph` 的编译缓存** —— 图是跨请求复用的，把每请求的 deadline 烘进闭包会让所有请求共用第一次那个时间。有一条专门的用例守着它 |
| **评测集加固** | `eval/qa_set.json`：32 → **46 条**，补语义改写 6 / 精确标识 5 / 跨篇陷阱 3，并补上原先完全没覆盖的 4 篇文档 |
| **加固后的分辨力**（local-hash 后端，Top-8） | 纯向量 95.7%（词面 96.8 / 语义 91.7）· 纯 BM25 95.7%（**词面 100** / 语义 83.3）· **混合 97.8%**（词面 100 / 语义 91.7）→ 混合明显最优，且"BM25 单独 100%"的饱和现象被打破 |
| **性能门禁** | `eval_baseline.py` 增加逐查询检索延迟（P50/P95）并与召回一起进门禁；基线里记 `latency_tolerance` |
| 用例 | `tests/test_agent_budget.py`（22 条）+ `tests/test_perf_gate.py`（13 条） |

### 6.1 M5a 期间发现的两个问题

| # | 问题 | 怎么发现的 | 处理 |
|---|---|---|---|
| M5-1 | **评测集饱和**：BM25 单独 100%、混合也 100% → 对"质量改进"零分辨力（也就是说：**M5d 配了 Key 也只会换来一句"还是 100%"**） | 实跑 `eval_baseline.py` 拿到真实数字 | 加固评测集（见上），并**重建基线**。★ 重建基线必须说清是"度量尺变严"而不是"系统退化"——新集上语义型召回从 100% 掉到 91.7%，那是新用例更难，不是系统变差 |
| M5-2 | **延迟门禁会 flaky**：同一份代码连跑两次，`vector.latency_p95_ms` 从 0.24ms 变 0.45ms（**+84%**） | 加完延迟门禁第一次跑就红了，而代码没变 | 加"测量下限"：**两边都低于 5ms 时不判失败、但必须打印**；只要有一边超过下限（例如 0.2ms → 10ms）就照判。★ 理由写在代码里：**一个会随机变红的门禁，最终会被所有人学会无视** |

### 6.2 M5a 的取舍记录

- **不硬超时**：硬砍会把已经花掉的钱和已查到的事实一起丢掉，用户拿到一个没有结论的错误。"以现有信息作答 + 如实说明被截断"严格优于"什么都没有"。
- **默认不限**：给整条链路默认加时限是行为变更，不该悄悄发生。
- **延迟门禁的容差是相对值（50%）不是百分点**：拿"5 个百分点"去卡毫秒没有意义。
- **`_percentile` 用最近秩法**：P95 应对应一次**真实发生过**的检索耗时，而不是插值出来的数字（更好解释，也更好定位）。

## 7. M5d 执行手册（真语义对比）—— 工具已就绪，只等 Key

M5d 要花钱调百炼 embedding，所以这一节是**给 Key 到位那一刻准备的操作手册**，
以及为它先做掉的那些"没有 Key 也必须先做"的事。

### 7.1 一条命令

```powershell
# 配好 .env 里的 DASHSCOPE_API_KEY 之后：
.venv\Scripts\python.exe scripts/compare_embedders.py --build
```

它会：① 把语义索引建到 **`data/index-semantic`**（**绝不动**正在用的 `data/index` ——
一份索引只能服务一个后端，覆盖它等于"为了做实验把可用状态弄没"）；
② 对两份后端各跑一遍 46 条评测 × 3 种模式；③ 打印对比表并写出
`eval/reports/embedder-compare-<时间>.md`。

零成本地先验证流程：`--local-only`（不需要 Key）。

### 7.2 判断口径（写死在输出里，避免数据出来后各说各话）

**真语义应当明显赢在"语义型"那一列。** 如果两列都没赢，就如实写
**"没赢、不引入"** —— 换后端要花钱，数据说了不算才引入。

参考：加固后的评测集上本地哈希是「纯向量 95.7% / BM25 95.7% / 混合 97.8%」，
其中混合的语义型 91.7%、词面型 100%。**真语义要证明的是"语义型那一列明显更高"**；
如果它只是把总体从 97.8% 抬到 98%，那不值得换。

### 7.3 为它先做掉的三件事（都不需要 Key）

| # | 事情 | 为什么必须先做 |
|---|---|---|
| 1 | `pipeline.evaluate(store=...)` 支持注入 store | 进程内的 store 是**单例缓存**，一份实现只能测一个后端。不开口子就只能在对比脚本里把召回率算法**再抄一遍** —— 两处实现必然漂移。现在对比与门禁跑的是**同一份代码** |
| 2 | 后端切换的报错**自带修复命令** | 配上 Key 的那一刻后端会从 local(512 维) 自动切到 dashscope(1024 维)，磁盘上的旧索引会被 `VectorStore.load` 拒绝。拒绝是对的（两套向量空间不能混算），但报错必须告诉人**下一步敲什么** —— 正在配环境时最不需要的就是翻文档找命令。现在它直接给出重建命令，并附"暂时不想配 Key 就清空它"的退路 |
| 3 | 对比脚本的守卫 | 没有 Key 时 `--build` 明确拒绝并给出两条路（配 Key / 用 `--local-only` 先验流程）；评测**本地**索引时进程内摘掉 Key（否则 auto 模式会选 dashscope，载入本地索引直接撞维度不匹配 —— 这是"对比"最容易被自己绊倒的地方） |

用例：`tests/test_embedder_compare.py`（14 条，零成本、不联网）。

### 7.4 M5d 交付时要写进文档的东西

- 三方对比表（local-hash / 真语义 / 混合 × 总体/词面/语义/陷阱 + P50 延迟）
- **一次性的 embedding 成本**（10 篇文档 / 91 块的量级很小，但要如实写）
- 结论：换还是不换，以及"为什么"（若没赢，就写没赢）
- 检索**延迟**的变化：真语义要多一次网络往返，P50 会比本地哈希高一个量级 ——
  这是它的真实代价，要和召回率一起摆出来让人权衡

## 8. M5d 实测结果（2026-10-02，真实百炼 Key）

> **结论：值得换。但第一版结论是错的 —— 错在度量上，而这一节的重点正是那个过程。**

### 8.1 数据（46 条用例 · 10 篇文档 / 91 块 · Top-8）

| 后端 | 模式 | recall@8 | **acc@1** | acc@3 | MRR | **语义列 acc@1** | P50 |
|---|---|---|---|---|---|---|---|
| local-hash（512） | 纯向量 | 95.7% | 65.2% | 84.8% | 0.751 | 25.0% | 0.13ms |
| | 纯 BM25 | 95.7% | 87.0% | 93.5% | 0.906 | 66.7% | 0.27ms |
| | **混合** | **100.0%** | 73.9% | 89.1% | 0.830 | 41.7% | **0.30ms** |
| text-embedding-v3（1024） | 纯向量 | 95.7% | 87.0% | 93.5% | 0.902 | **83.3%** | 323ms |
| | 纯 BM25 | 95.7% | 87.0% | 93.5% | 0.906 | 66.7% | 0.26ms |
| | **混合** | 97.8% | **80.4%** | **95.7%** | 0.877 | **66.7%** | 319ms |

**真语义明显赢在它该赢的地方**：语义列 acc@1 **+25.0pp**（混合）/ **+58.3pp**（纯向量）；
混合检索整体 acc@1 **+6.5pp**、acc@3 **+6.6pp**。

### 8.2 ★ 第一版结论是错的，根因在指标（这一节最该记住的）

1. **第一次比，我只看了 recall@8** → 得到"真语义没有整体收益（100% → 97.8%），
   延迟贵约 1000 倍 → 不值得换"。这个结论**看起来完全有数据支持**。
2. 抽查时发现一条真实提问「磁盘写满了怎么办」在本地后端 **top-3 完全没命中**，
   而评测集说 100%。同一批抽查里真语义 3/4 修好。
3. 追下去发现**根因是指标本身没有分辨力**：语料只有 10 篇文档、口径却是 top-8 ——
   "正确答案在不在前 8"几乎必然命中（随机取 8 块也有约五成以上概率命中）。
   于是分数长期停在 95~100%，**区分不出"排第 1"和"排第 8"**，
   而那两者的使用体验完全不同。
4. 于是加了 **rank-aware 指标（acc@1 / acc@3 / MRR）**，用**同一批数据**重测 →
   结论直接翻转（见 8.1）。顺带还暴露了两个旧指标掩盖的问题：
   · 本地后端的混合检索 recall@8 = 100%，而 **acc@1 只有 73.9%**；
   · **混合（生产默认）的 acc@1 反而低于纯 BM25 13 个百分点** ——
     本地哈希的向量路在拖后腿。

**教训**：**度量不对，结论就会反**，而且反得很有说服力。
这是"评测集/指标没有分辨力"这个主题在本项目里第三次出现
（前两次见 §6.1 与 `docs/evaluation.md`），这次终于把根因（top-k 口径 vs 语料规模）
修在了指标层：rank-aware 指标已经进基线、进 CI 门禁。

### 8.3 取舍与代价

- **延迟**：每次**查询**多一次网络往返（0.30ms → 319ms）。
  相对一次问答本身 6–20 秒，**可忽略**。
  一次性成本：91 块的建索引 embedding（很小）。
- **词面型仍略弱**（真语义向量 93.5% vs 本地向量 96.8%）→ 生产仍应走**混合**，
  让 BM25 守住精确标识（`ERROR 1040` 这类）。这也再次说明"混合"这个默认是对的。
- **一条融合弱点值得记下**：本地 BM25 单路词面型 recall@8 = 100%，
  而真语义混合只有 96.8% —— **RRF 会被"自信但错误"的一路拖累**
  （向量路把 BM25 找对的那条挤出了前 8）。这是下一步的改进候选，
  需要新数据支持再动，不凭这一条就改。

### 8.4 运维耦合（必须知道）

**索引与 Key 必须匹配**：配了 Key 而 `data/index` 还是 local 建的，
`VectorStore.load` 会**拒绝加载**并给出重建命令（M5d 准备阶段做的那个报错）。

**当前仓库状态**：Key 已**注释停放**在 `.env`（原值保留在同一行），
服务用本地索引继续跑 —— 这样"服务可用"与"随时可重测"都成立。
要切到真语义：

```powershell
# 1) 取消 .env 里 DASHSCOPE_API_KEY 那一行的注释
# 2) 用真语义重建**在用**的索引（data/index）
.venv\Scripts\python.exe -m app.rag.pipeline build
# 3) 重新标定基线（后端变了，基线必须跟着变）
.venv\Scripts\python.exe scripts/eval_baseline.py --update
```

**为什么我没替你直接切**：切过去意味着每次查询都要联网调一次 embedding
（延迟与持续成本都变了）。数据支持这个选择，但"要不要开始为检索付费"
是你的运行决策 —— 命令在上面，一条一条可回退。
